# 关系演化（v0.2）· 设计文档

- 日期：2026-11-13
- 状态：待批准
- 范围：`lib/host/pulse.js`（新增）、`lib/host/model.js`、`client.js` 渲染层与时间轴 UI。

## 1. 意图与原因

用户原话（`m00035`）：「想看清某段时间关系怎么变的」。

v0.1 已经把星图做成一张像星系的关系图，但它只回答「谁重要」，不回答「怎么变的」：

| 现象 | 代码事实 |
|---|---|
| 拖时间轴只有节点在动 | `client.js:1340-1351` `nodeAlpha()` 用 `node.series[index]`，节点会按桶亮暗 |
| 关系线是死的 | `lib/host/model.js:346-355` chat 边的 `weight` 是 `person.total`（全生命周期总量），没有逐桶序列 |
| 回放只有一种速度 | `client.js:2342` 固定 `setInterval(..., 420)` |
| 抽屉看不出关系走势 | `lib/host/model.js:543` 只有该会话自己的 `monthly`，没有「谁和谁」的曲线 |

所以「关系在时间上的变化」这件事，图里根本没有数据支撑——节点亮暗是会话活跃度，不是关系强度。

## 2. 目标与非目标

**目标**

- 回放时能看到**关系本身**在呼吸：当期热的关系浮现并变亮，当期断联的关系直接消失。
- 退出回放立刻回到 v0.1 的干净星系（边全隐），美学不回退。
- 抽屉里能读到「我和这个人」这段关系随时间的走势（含谁更主动）。
- 播放速度可调（慢/正常/快）。

**非目标**

- 不做圈子迁移分析、不做 Louvain（v0.3）。
- 不改 Host 的 JSON 契约主干（只**新增**字段，不删不改现有字段）。
- 不做框选时间窗口整图重算（C 方案，留作后续延伸）。
- 不改「边默认全隐」这条 v0.1 决定。

**反目标**

- 回放时整屏糊成一张网——那就比不做更糟。
- 关系强度用绝对消息条数——不同人的聊天量差 10 倍，画面会被高频关系独占。

## 3. 采用的方案与取舍

### 考虑的方案

**A. 边带逐桶序列 + 回放浮现（采用）**
给每条 chat 边加 `series`（逐桶计数）与 `sentSeries`/`recvSeries`（我发/对方发）。回放时按当期强度决定这条边是否画、多亮、多粗。

**B. 只让节点更准确地反映当期活跃**
改动最小，但用户问的是「关系」，节点亮暗表达不了「谁和谁」。
**否决理由**：回答不了用户的问题。

**C. 边常显，不靠回放**
最直观，但违背 v0.1 已验收的美学（真星系没有连线）。
**否决理由**：用户为「像星系」返工过一轮，不能反过来。

### 取舍理由

- **为什么强度要相对化**：用 `baseline`（该桶所有关系的均值）+ 指数饱和 `1 - exp(-v/baseline)`。绝对条数下，一个每天聊 200 条的人会把所有人压成暗线；相对基线下「这段时间对这个人来说算多」才是可比的。
- **为什么时间键抽到 pulse.js**：造图（Host）与回放取桶（渲染层）必须用同一套键。以前 weekKey 藏在 model.js 里，渲染层要重写一遍就一定会漂移，漂移的表现是「边和节点整体错开一格」，极难发现。
- **为什么粒度在 400 天处从周切到月**：沿用 model.js 现有规则，不新增概念。

### 用户已确认的取舍

- 浅色主题画布保持深空（v0.1 裁定），本设计不动。
- 回放退出后边恢复全隐（本设计新增，见 §4.3）。

## 4. 关键设计

### 4.1 数据：边新增字段（只增不改）

```
edge.series: number[]      // 与 graph.timeline 等长，逐桶消息数
edge.sentSeries: number[]  // 我发出的，逐桶
edge.recvSeries: number[]  // 对方发来的，逐桶
```

只有 `type === 'chat'` 的边有；其余边类型（group-member / co-occurrence / topic）保持原样。

规模：2093 节点 ≈ 2100 条 chat 边 × 3 序列 × 桶数（真机 ≈ 60–100 桶）≈ 60 万数字，JSON 约 2–4 MB。**这是本设计最大的代价**，缓解见 §6。

### 4.2 时间键与序列（`lib/host/pulse.js`，纯函数）

- `bucketKeyOf(seconds, now)`：`now - 400 天` 以内用 `weekKey`，否则 `monthKey`。与 model.js 原表达式等价，改为唯一实现。
- `seriesForBucket(messages, timeline, now)`：桶 key → 下标映射后摊平，O(消息数)。
- `baselinePerBucket(seriesList, length)`：每桶只对「有消息的关系」求均值。
- `edgePulse(series, scale, index, total, maxTotal)`：`index < 0`（全部时间）时退回 `total/maxTotal`，保证非回放状态行为与 v0.1 一致。

### 4.3 渲染：回放时关系浮现

- `view.timeIndex >= 0` 视为「回放中」。
- 回放中：`edgesToDraw` 先按当期强度过滤（强度 0 的边直接不画），再按强度取前 N 条。
- 线的亮度：`alpha = 0.10 + pulse * 0.34`；线宽：`0.7 + pulse * 1.6`。
- 回放中**保留**原有的悬停/选中高亮路径（高亮的边永远画，不参与过滤）。
- `timeIndex < 0`：完全走 v0.1 老逻辑（top12 极淡线），像素级不变。

### 4.4 播放速度

三档：慢 700ms / 正常 420ms / 快 200ms，默认正常。存在 `view.playbackMs`，UI 放在时间轴 `播放``全部` 按钮之后。

### 4.5 抽屉：关系热度曲线

在「月度活跃」卡片下方新增一张「关系热度」卡片（仅 person/group 节点、且该节点有 chat 边时显示）：

- 曲线：该边 `series`（逐桶关系强度）。
- 双色叠加：我发（冷）/ 对方发（暖），让人一眼看出主动性变化。
- 当前回放位置高亮一根竖线。

## 5. 性能预算

- Host 侧：`seriesForBucket` 对 2600 条演示消息 ≈ 微秒级；真机 20 万消息 ≈ 数十毫秒，只在建图时跑一次（建图本身已有缓存）。
- 渲染侧：回放时每帧多算 `edges.length` 次数组查表（≈2100 次），可忽略；过滤在 `edgesToDraw` 里一次完成。
- 传输：见 §4.1，2–4 MB 是新成本。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| JSON 涨到 2–4 MB，首次加载变慢 | 先落地再看真机；若超过 6 MB，退化为「只给 top 400 关系带序列」 |
| 400 天粒度切换处相邻两桶粒度不同 | 沿用既有规则，不做特殊处理；界面上桶标签本身已经写明是周还是月 |
| 渲染层重写一遍强度公式导致与 Host 漂移 | 测试里同时加载 `pulse.js` 与 `client.js` 的 `__test` 导出，对同一输入断言两边结果相同 |
| 回放时边太多糊成网 | 强度 0 过滤 + top N 截断 + 亮度上限 0.44 |

## 7. 验证方式

- `test/pulse.test.mjs`：时间键、序列、强度、基线（11 条，已写）。
- `test/edge-pulse.test.mjs`：`client.js` 与 `pulse.js` 的强度公式一致；回放态边过滤；非回放态保持老行为。
- `npm test` 全绿。
- 真机：回放时截图对比「当期有关系的边浮现、断联的边消失」；退出回放确认回到干净星系。
