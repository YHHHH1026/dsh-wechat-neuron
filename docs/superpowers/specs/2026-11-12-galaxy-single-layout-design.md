# 星系图单布局重做 · 设计文档

- 日期：2026-11-12
- 状态：待批准
- 范围：`client.js` 的渲染层（`NeuronRenderer`）。Host 侧数据契约不变。

## 1. 意图与原因

用户原话：「目前星图太丑了，完全不像星系，其实不需要几个布局，只需要一个星系图布局就行了，重点是把星系图整高端、简约，要和真正的星系一样的效果。」

两件事：

1. **砍到只剩一个布局**——现在有 6 个（`client.js:37-44`：galaxy / sphere / helix / cluster / radial / force）。用户认为多布局是噪音，要一个做到极致。
2. **让那个布局真的像星系**——不是「发光线条 + 撒点」，而是天文照片的观感：核球、薄盘、对数螺旋臂、尘埃带、幂律亮度分布的星点。

**为什么现在不像**（实测代码定位，不是审美判断）：

| 现象 | 代码事实 |
|---|---|
| 旋臂是画出来的粗线 | `client.js:919-930` 用 `lineWidth = max(24, w*0.042)` 的 `stroke()` 描弧，是矢量线条不是密度 |
| 星尘均匀撒满盘面 | `client.js:939-942` `radius = pow(rnd,0.62)*min(w,h)*0.62`，与旋臂无关，无聚集 |
| 布局不是螺旋 | `client.js:627-636` 半径按排名 `150+t^0.62*560`，角度含 `index*0.06`（同半径被均匀摊开），`y = sin(index*1.7)*46` 是随机抖动 → 无薄盘、无核球 |
| 节点是圆球 | `client.js:1049-1071`「白核 + 彩色光晕」渐变圆，`radiusOf` 最大到 34px（`client.js:592-599`） |
| 亮线网罩住星系 | `client.js:985-1019` **所有边无条件绘制**，4 种颜色 + 脉冲 |

## 2. 目标与非目标

**目标**

- 单一「星系」视图，达到可直接截图当壁纸的观感。
- 深色 / 浅色主题下都成立。**画布本身恒为深空**（已与用户确认）：星系靠加性混合的发光星点成型，近白底上加性会直接饱和成一片白，星点全部消失。浅色主题只影响面板、侧栏、标签、边框与抽屉，画布像一张天文照片嵌在浅色面板里。
- 2093 节点 / 3556 边的规模下稳定 60fps。
- 关系（边）信息不丢失，改为按需浮现。

**非目标**

- 不引入 WebGL、不引入任何第三方依赖（`package.json` 现在零依赖，保持）。
- 不改 Host 侧数据模型、不加新字段、不碰 v0.2/v0.3 的功能项（chatlog 适配器、CSV 导入导出、LOD、Louvain 等一律不在本设计内）。
- 不做布局切换器、不做布局记忆。
- 不做浅色反极性（白底深星）——已否决，见上。

**反目标**（技术上成功但算失败）

- 变成「更精致的矢量插画」——如果最终仍是几条描边曲线，本次就是失败的。
- 为了像照片而牺牲可读性：找不到人、看不懂谁重要。
- 弱连接节点在内臂挤成一条实心带，把旋臂糊成一块。

## 3. 采用的方案与取舍

### 考虑的方案

**A. 密度场 + 加性点星（采用）**
用对数螺旋密度函数生成 1.5–2 万星点，叠加指数盘 + 核球 + 幂律亮度，一次性预渲染到离屏 canvas，每帧只做一次 `drawImage`。天花板 = 天文照片。

**B. 保留描线法，把工艺做精**
标准对数螺旋 + 旋臂聚集粒子 + 多道 bloom + 压小节点光晕。改动约 120 行，快；但天花板是「矢量插画」，永远差一口气。

**C. WebGL + bloom shader**
上限最高，顺带解决 8000+ 节点性能。但等于换渲染后端，且零依赖手写 WebGL，本次不做。

### 取舍理由

选 A。B 的天花板正是用户抱怨的那个东西（「不像星系」），精修描线法只能得到更亮的线条，得不到密度。C 超出本次范围，且在 2000 节点量级 Canvas2D 完全够用——瓶颈在「看起来假」，不在帧率。

**已知代价**：`draw()` 与 `applyLayout()` 基本重写（约 400–500 行），旧的多布局分支全部删除。可接受，因为用户明确说不要多布局。

### 用户已确认的取舍

> 「真星系里不存在连线，可关系图谱的价值恰好在边。」

**决定：边默认完全不画。** 仅在悬停 / 选中某个节点时，以细光束形式浮现该节点的一跳邻居边，并脉冲一次；移开即消失。用户已通过「按照你的建议来」批准。

## 4. 关键设计

### 4.1 相机改为正交投影

这是承重点。星系盘要作为**一张倾斜的位图**贴上去，而 Canvas2D 只能做仿射变换；透视投影下倾斜圆盘是投影变换，无法用 `setTransform` 表达，会导致「位图盘面」与「节点位置」始终错位。

所以星系视图改用**正交投影**（天文照片本身就是正交的），透视只保留为深度排序与大小衰减的依据。

下面的公式**沿用现有 `project()`（client.js:822-840）的符号约定**，避免实施时把 yaw 方向搞反：

```
旋转：x1 = x·cosY - z·sinY
      z1 = x·sinY + z·cosY
俯仰：y2 = y·cosP - z1·sinP
      z2 = y·sinP + z1·cosP

屏幕：sx = cx + panX + x1·scale
      sy = cy + panY + y2·scale
      depth = z2            // 仅用于排序与衰减，不参与屏幕坐标
      scale = fit · zoom     // 单位：CSS px / 世界单位
```

**世界坐标归一化**：星系几何在 `R = 1.0` 下定义（`layoutGalaxy()` 直接写 ±1.15 量级的坐标）。`computeFit()` 因此变成 `fit = wanted / maxRadius`，`wanted = min(w,h)*0.46`，`fit` 的量级约 `0.4*min(w,h)`。

盘面位图使用**同一个变换**。**关键：不能用 `setTransform` 覆盖基准**——`resize()`（`client.js:506`）已经把画布基准设成 `setTransform(dpr,0,0,dpr,0,0)`，而 `project()` 返回的是 CSS 像素。正确做法是先恢复 DPR 基准，再用 `transform()` 把仿射叠加上去：

```js
ctx.setTransform(dpr, 0, 0, dpr, 0, 0)      // 恢复 CSS 像素基准
ctx.transform(
  cosY * s,             // a
  -sinY * sinP * s,     // b
  -sinY * s,            // c
  -cosY * sinP * s,     // d
  this.w / 2 + panX,    // e   ← 必须用 w/2, h/2
  this.h / 2 + panY,    // f
)
// 位图覆盖世界 [-R, R]²，R = 1.25（1.15 外圈 + 薄盘厚度余量）
ctx.drawImage(diskSprite, -R, -R, 2 * R, 2 * R)
ctx.setTransform(dpr, 0, 0, dpr, 0, 0)      // 收尾恢复
```

三个坑，每一个都会让盘面和节点错开：

1. **DPR**：若直接 `setTransform(cosY*s, …)`，会把 `dpr` 基准扔掉。`dpr=2` 时盘面变成节点的一半大、位置也偏移一半。必须 `setTransform(dpr…)` + `transform(…)`。
2. **`draw()` 作用域里的 `cx`/`cy` 是陷阱**：`client.js:871-872` 定义的是 `cx = this.w/2`、`cy = this.h * 0.48`，而 `project()`（`client.js:836`）用的是 `h/2`。直接复用这两个变量会让盘面整体下沉 `0.02*h`（900px 高时 18px），恰好就是本设计声称「已消除」的那种错位。**必须写 `this.w/2 + panX`、`this.h/2 + panY`**。
3. **盘面跨度必须覆盖整张盘**：`drawImage` 若用 `-1,-1,2,2`，正方的精灵会把半径 1.15 的圆盘四边裁成直边（约 9.5% 星点落在方框外，圆周出现直线切口）。用 `R = 1.25`，且位图**就按 `[-1.25, 1.25]` 生成**，`2R = 2.5` 世界单位。

`drawImage` 的第 3/4 参用**世界单位**（`2*R`）而不是位图像素尺寸 `W`：位图自己的分辨率（3072²）只影响锐度，不影响布局，换分辨率不用改这里。

这样盘面与节点**在任何 yaw/pitch/zoom 下都严格对齐**，不需要手工对参。实施时**先把「盘面 + 十字准星」单独跑通再上节点**——这是本设计的第一个里程碑，别把两件事混在一起调。

**深度线索**（重要，别以为 `scale` 会带深度）：`scale = fit · zoom` **不含任何深度项**，所以正交下节点屏幕尺寸完全一致。设计上要的正是这个（天文照片不做近大远小），但 §4.1 说的「depth 用于排序与衰减」必须真的把**衰减**实现出来，否则所有星点等亮度、层次全无。在排序之外，按深度做一次很小的半径/透明度调制：

```js
const k = (p.depth - zMin) / Math.max(1e-6, zMax - zMin)   // 0 = 最近, 1 = 最远，每帧算一次
const radius = node.r * (0.80 + 0.45 * (1 - k))            // 近端 +25%，远端 −20%
const alpha  = baseAlpha * (0.70 + 0.35 * (1 - k))         // 近端亮、远端暗
```

注意：加性混合（`'lighter'`）下**绘制顺序在视觉上是无操作**（加法可交换），所以这个深度调制是唯一的层次来源——排序本身只对「半透明叠加」有意义。别指望排序。`zMin`/`zMax` 每帧遍历一次投影结果即可，O(n)。

**`pick()` 必须改**（`client.js:1157-1173`）。它现在写 `Math.max(6, node.r * p.scale * 0.9)`。`node.r` 是**屏幕像素**（`radiusOf` 返回 9、13 这类值），而 `p.scale` 现在从 `0.27` 涨到 `fit·zoom ≈ 432`——**涨了约 1600 倍**。于是 `node.r=9` 的命中半径变成 `9 × 432 × 0.9 ≈ 3500px`，整个画布都是热区。更糟的是 `pick()` 用 `distance / radius` 比大小，半径最大的 `self` 会在任何位置胜出，永远选不到别人。改成与绘制半径一致、不含 `p.scale`：

```js
const radius = Math.max(9, node.r)
```

**`p.scale` 的其余消费者全部要改**（`ops_grep` 实测只有三处，`pick()` 已单独说明）：

| 行 | 现有代码 | 正交后为什么会坏 |
|---|---|---|
| `client.js:991` | `alpha *= Math.min(1, (pa.scale + pb.scale) / 1.6)` | 参数量级 `864/1.6 = 540` → 恒被夹为 `1`，这条边深度衰减变成死常数。删掉 |
| `client.js:1043` | `persp = Math.max(0.62, Math.min(1.9, sqrt(p.scale)*1.1))` | `sqrt(432)*1.1 ≈ 22.9` → 恒为 `1.9`。**所有**节点都被放大 1.9 倍：self 24.7px、person 17.1px、topic 5.3px —— 直接把 §4.3 的 `radiusOf` 收小全部抵消。删掉 `persp`，改用上面的深度调制 |
| `client.js:1163` | `radius = Math.max(6, node.r * p.scale * 0.9)` | 见上，改用 `Math.max(9, node.r)` |

**连带**：`client.js:1104` 的标签门槛是 `radius > 8.5`。删掉 `persp` 后 person 的 `radius` 回到 5.9–9 区间，`8.5` 这条线会几乎不出标签。按 §4.4 第 8 步改到 **`radius > 5`** 或选中/聚焦，两者必须同时改，否则改完看不见名字。

`computeFit()`（`client.js:511-531`）有**四处**要改，漏改任何一处都会让图缩成一点：

1. `const projected = maxRadius * (FOV / 1000)` → `const projected = maxRadius`。
2. `Math.max(0.25, Math.min(4, wanted / Math.max(1, projected)))` 的 **`4` 上限必须去掉**。归一化后 `fit ≈ 360`（1440×900）或 `240`（800×600），被夹成 `4` 后盘面半径只有约 5.5px —— 屏幕中央一个点。改成 `Math.max(0.25, wanted / Math.max(1e-6, projected))`。
3. **空图提前返回**（`client.js:513`）：`if (list.length === 0) { this.fit = 1; return }`。盘面是**无条件绘制**的，`fit=1` 时整张星系只有 ~25px 宽。改成 `this.fit = R_GALAXY_MIN_FIT`，即 `0.46 * Math.min(this.w, this.h) / R_GALAXY`（`R_GALAXY = 1.15`）。
4. `const FOV = 900`（`client.js:424`）随之变成死代码，删掉；`project()` 里 `FOV / Math.max(180, depth)` 整句替换为 `scale`。实测 `FOV` 只在 `424`（定义）/`529`（这里）/`833`（`project`）三处出现，删干净没有遗漏。

82 分位的采样逻辑保留。**但下限不能设成 `0.6`**：`Math.max(0.6, pick)` 会让 `fit = 0.46*min/0.6 = 0.77*min`，盘面半径 `1.15*0.77*min = 0.88*min`，图会溢出画布（应为 `0.46*min`）。下限用 **`1.15`**（即 `R_GALAXY`），此时 `fit = 0.46*min/1.15 = 0.4*min` —— 与正常情况连续。更稳的写法是直接夹 `fit`：`this.fit = Math.min(wanted / Math.max(1e-6, maxRadius), 0.46*min(w,h)/1.15)`。

### 4.2 星系几何

所有尺度以 `R` = 盘面半径（归一化 1.0）为单位。

**对数螺旋臂**

```
r = r0 · exp(tan(i) · θ)          i = 13°（tan i ≈ 0.231）
θ(r) = θ_arm + ln(r / r0) / tan(i)
```

4 条臂：起点按 `armStarts = [0, π/2, π, 3π/2]`（**均匀 90° 交错**）；主臂为索引 0、2，次臂为索引 1、3（星点密度权重 0.45）。`r0 = 0.12`。

> 注意别把次臂写成 `π/4`：`0, π/4, π, 5π/4` 的间隔是 `45°,135°,45°,135°`，出来是「两对贴在一起的臂」，读起来像 2 条臂被撕开，不是星系。

**盘密度**（指数盘，`h = 0.28`）
径向采样用两个均匀分布相乘的经典反演，无查表：

```
r = -h · ln(u1 · u2)        // u1,u2 ~ U(0,1)
```

> 这里刻意带上面积元 `r dr`：`p(r) ∝ r·e^(-r/h)` 正好是 `Gamma(2, h)`，而 `-h·ln(u1·u2)` 就是它的精确反演。若漏掉 `r dr` 直接用 `-h·ln(u1)`，核心会过密、外盘塌空。

**臂内 vs 臂间**：70% 星点贴臂，30% 均匀铺满 `θ ∈ [0,2π)` 形成弥散盘。**这一条是「不像两条画上去的线」的关键**，不可省。

贴臂的角宽按**弧长恒定**给，不是按角度恒定：

```
σθ = clamp(0.11 / r, 0.06, 0.55)
θ  = θ_arm(r) + gauss(0, σθ)
```

弧宽恒定 = 内圈的角度散布大、外圈的角度散布小，这恰好是对数螺旋臂在真实星系照片里的样子（臂在核球附近被压得几乎糊掉，到外盘才拉成清晰的丝带）。

**薄盘**：`z = gauss(0, 0.055 · r^0.5)`，外圈更厚（真实盘有外翘）。

**核球**：15% 星点，`r_b = -0.10·ln(u1·u2)` 截断到 0.25，球对称方向，`z` 不做压缩。

**亮度幂律**：`b = 0.08 + 0.92 · u^4`（绝大多数是暗星，少数亮星撑起结构感）。每个星点画成 2–3px 的软高斯点，`globalCompositeOperation = 'lighter'`。

**色温**：默认蓝白 `#cfe0ff`；`r < 0.3` 的核球区混入暖金 `#ffe6c4`；臂上 3% 概率给 HII 电离氢的品红 `#ff9ecf`（真实星系里最抓眼的细节）。

**尘埃带**：在盘面位图里、星点**之后**用 `globalCompositeOperation = 'destination-out'` 沿臂内缘画若干条低 alpha 的暗带，撕裂星点分布。这一步把「发光斑块」变成「有结构的盘」。

**星点数量**：**固定 20000**（不随视口变，见 §5）；盘面位图固定 **3072×3072**，覆盖世界 `[-1.25, 1.25]²`。

> **位图坐标 ≠ 屏幕像素**，这里有个必须说清的换算：位图跨度 `2R = 2.5` 世界单位，3072px 宽即 **1 位图像素 = 2.5/3072 ≈ 0.000814 世界单位**。`fit = 0.46·min(w,h)/1.25`。
>
> | 视口 | `fit` | `s = fit·zoom` | 1 位图像素 ≈ | 暗星 2–3 点位图像素 | 亮星 6–14 点位图像素 |
> |---|---|---|---|---|---|
> | 1440×900, zoom 1.2 | 331 | 397 | 0.32 屏幕像素 | 0.65–0.97 | 1.94–4.53 |
> | 1440×900, zoom 3.6 | 331 | 1192 | 0.97 屏幕像素 | 1.94–2.91 | 5.82–13.58 |
> | 800×600, zoom 1.2 | 221 | 265 | 0.22 屏幕像素 | 0.43–0.65 | 1.29–3.02 |
> | 800×600, zoom 3.6 | 221 | 795 | 0.65 屏幕像素 | 1.29–1.94 | 3.88–9.06 |
>
> 暗星在默认缩放下只占半个屏幕像素——这正是暗星该有的样子，是对的（靠加性叠加上去成雾）。但亮星（`b > 0.9` 的约 1%）不能指望同一个尺寸，要单独画成 **6–14 位图像素**的高斯点才撑得起结构感。**如果实施时把「2–3px」当屏幕像素理解，盘面会变成糊上一层的亮毛，直接毁掉设计。**

同理，位图像素密度（3072²）决定的是**锐度**，不是**星点大小**：想要更细腻的尘埃丝，提高分辨率；想要更大的星，改星点半径的位图像素值。两件事别混。

### 4.3 节点如何落在星系上

节点不是「另画一层」，而是**嵌进盘面结构**：

- `self`：核球正中心 `(0,0,0)`。
- `person`：半径由重要度反推 `r = 0.10 + (1 - score/100)^1.35 · 0.92`（重要的人靠近核心），角度取最近的臂 `θ_arm(r)` + 抖动。**落在臂上**，所以视觉上「人是星团里的一颗亮星」。
- `group`：同一公式，额外沿 z 抬 `+0.06`，做出盘面之上的层次。
- `topic`：外圈尘埃区 `r ∈ [0.85, 1.15]`，`z` 压到盘面下 `-0.04`，半径极小（`radiusOf` 给 1.6–2.8px），颜色品红但 alpha 低。默认更淡，接近盘面里的暗尘。

**防重叠（必须做，否则重要的人会叠成一坨）**：纯 `r = f(score)` 会让分数接近的人挤在同一半径、同一条臂上。按分数降序依次落位，每人挑当前**承载数最少**的那条臂：

```js
const load = [0, 0, 0, 0]                       // 4 条臂的已用名额
for (const node of peopleByScoreDesc) {
  const r = 0.10 + Math.pow(1 - node.score / 100, 1.35) * 0.92
  // 该半径处各臂的角度
  const arms = armStarts.map(a => armAngle(a, r))
  let pick = 0
  for (let i = 1; i < 4; i += 1) if (load[i] < load[pick]) pick = i
  // 同臂内再沿角度错开，避免同半径同臂堆叠
  const spread = 0.075 * load[pick]
  const theta = arms[pick] + spread + (hash(node.id) - 0.5) * 0.05
  load[pick] += 1
  targets.set(node.id, [Math.cos(theta) * r, jitterZ(r), Math.sin(theta) * r])
}
```

`hash(id)` 是把字符串 id 折成 `[0,1)` 的小函数（FNV-1a 取模即可），保证**同一份数据每次布局完全一致**——不能每次重排都跳一下。

`armAngle(arm, r)` 就是 §4.2 的 `θ_arm(r) = armStart + ln(r/r0)/tan(i)`。

`jitterZ(r)` = §4.2 的薄盘分布 `gauss(0, 0.055 * sqrt(r))`。

**低分节点必须偏离臂（这条是「旋臂清晰」与「找得到人」的唯一交点，不可省）**：上面 `r = f(score)` 的公式对所有 person 通用，但弱关系数量极大（`minTier='weak'` 是默认值，`groupOnly` 成员 `score` 只有 8）。如果每个弱节点都严格贴臂，内臂会挤成一条**实心带**，旋臂就被糊没了——这直接违反「像星系」这个目标。

规则：以 `score` 的第 60 分位（记作 `S60`，按当前图实时算）为界——

- `score >= S60`（约前 40%，通常是几百人）：**严格贴臂**，用上面的防重叠算法。这些人构成旋臂的「星团」，是视觉结构的主体。
- `score < S60`：**不贴臂**，按半径分位推进弥散盘。角向用 `theta = hash(node.id) * 2π` 均匀分布（确定性），半径在基准 `r(score)` 上再乘一个 `0.75 + 0.5*hash(node.id+'r')` 的抖动，让它们铺在臂间与臂外侧。这些人构成 §4.2 说的「30% 臂间星」的对应物——**人眼看到的旋臂由高分节点定义，低分节点提供弥散盘的质感**。

这样既保住了臂的清晰度，又不会「只看得见最亮的几十个」：弱关系仍在图上、仍可搜到、仍可点开，只是不作为结构骨架。

`radiusOf()`（`client.js:592-599`）整体收小：`self` 19 → 13；`person` 上限 15 → 9；`topic` 上限 6.6 → 2.8。节点是「星」，不是「球」。另外弥散盘里的弱节点命中太小的不好点，`pick()` 的 `Math.max(9, node.r)` 下限（§4.1）就是为它们兜底的。

**归一化后的取整**：注意 `r`、`theta` 都已是归一化世界单位，`applyLayout` 写进 `targets` 的就该是 `±1.2` 量级。**不要再乘 320/430/560 这类旧尺度**——`computeFit` 会把它们放大到屏幕。

**`spread()` 也要跟着归一化**（`client.js:574-590`）。它现在把初始位置撒在半径 `320` 的球壳上；布局目标只有 `±1.2`，于是入场动画会变成「几百个点从屏幕外 300 倍远处飞进来」，缓动 `ease=0.09` 要 ~110 帧（约 1.8 秒）才收拢，那两秒整个画布是空的。改成撒在 `±1.2` 球壳上，入场就是一次轻微沉降，而不是远航。

顺带：`spread()` 里的 `Math.random()` 只影响**初始位置**，不影响最终布局（最终位置由 `layoutGalaxy()` 决定），可以保留；但 §4.3 里 `hash(node.id)` 的抖动必须确定性，否则每次刷新同一批人的位置都会跳。

### 4.4 绘制顺序（每帧）

1. 背景：深空径向渐变（复用现有），浅色为米白星云。
2. 核球辉光：1 个大半径径向渐变（复用现有，`client.js:888-906`）。
3. **盘面位图**：单次 `drawImage`（4.1 的矩阵）。
4. 节点星点：加性混合（`'lighter'`），**按 §4.1 的深度调制**（`k` → 半径/alpha）拉开层次。不需要排序：加性混合下绘制顺序在视觉上可交换，排序只是白花的 `O(n log n)`。光晕用预渲染的小 sprite（每个 tier 颜色一张 32×32），不再每帧建 `createRadialGradient`（现在每节点每帧建 2 个渐变，是主要 CPU 开销）。
5. 星芒：仅 `self` / 选中 / 聚焦 / `score ≥ 70`。
6. **边：默认不画。** `highlight !== null` 时才画，且只画与 highlight 相关的一跳边，`alpha = 0.35`、细、加性；选中时该边脉冲一次。
7. 暗角。
8. 标签（**必须在暗角之后**）。

> 第 7/8 步的顺序是硬约束，别照搬现在代码里的顺序。现有 `draw()` 把暗角画在节点**之前**（`client.js:958-964`，紧跟星尘），所以节点和标签不受暗角影响。新顺序里暗角是收尾层，若把标签放在暗角之前，边缘人物的名字会被压掉一半。标签放最后，`globalCompositeOperation` 已是 `source-over`，不受加性混合影响。

标签本身：沿用现有避让逻辑，但默认只在 `radius > 5` 或选中/聚焦时出，且去掉背景色块，改 `shadowBlur` 光晕描边（更简约）。

**关系（边）的可达性兜底**——这是「边全隐藏」方案唯一的风险点，必须显式解决，不能只靠「精确命中一颗 2–9px 的星」：

1. `hover` 也参与 `highlight`（现有代码里 hover 只喂 tooltip，`client.js:1216-1228`；`highlight` 只来自 selected/focus，`client.js:969-971`）。悬停即显影该人的一跳关系，移开即消失。这样「看一眼谁跟谁有关系」不需要点击。
2. `pick()` 在**没有精确命中**时，退化为取**屏幕上最近**且距离 < 28px 的节点（已知所有 `p.sx/p.sy`，一遍线性扫描即可，2093 个点无所谓）。弱节点在弥散盘里很小，这是把它们变成可点目标的唯一现实办法。
3. **top-N 关系常显**：全图度数最高的 12 条边（按 `weight`）保持极淡常显（`alpha 0.10`、1px、不着色），作为「这是关系图而不是纯装饰画」的最低限度提示。选中/悬停时这些线让位给高亮边。

三条一起做，§8「边全隐藏后信息丢失」这条风险才算真关闭。只做第 1 条是不够的。

## 5. 性能预算与位图生命周期

| 项 | 目标 |
|---|---|
| 盘面位图生成 | 一次性 ≤ 400ms（2 万星点，3072²） |
| 每帧 | 1 次 `drawImage`(盘面) + N 次 `drawImage`(sprite) + 标签文本 ≤ 8ms @ 2093 节点 |
| 重建时机 | **仅首次挂载 + DPR 变化**。旋转、缩放、resize、主题切换**一律不重建** |

**位图与视口解耦，星点数固定**（这是上一版文档自相矛盾的地方，现在定死）：

- 星点数**固定 2 万**，不随视口变化。视口变化只改变 `fit`（显示尺度），不改变盘面内容。
- 位图分辨率 **3072×3072**，覆盖世界 `[-1.25, 1.25]²`，即 `3072/2.5 ≈ 1229 位图像素/世界单位`。
- **缩放不重建**，代价核算过：`s = fit·zoom`，zoom 上限 3.6 时 `s ≈ 432×3.6 = 1555`，1 位图像素 = `(2/3072)×1555 ≈ 1.01` 屏幕像素——刚好到轻微可辨的边界，可接受。zoom 1.2 时是 0.28 屏幕像素，暗星仍是亚像素，正确。若日后觉得高倍下不够锐，把分辨率提到 4096 即可（其余代码不用改，因为 `drawImage` 用的是世界单位跨度）。
- 主题切换不重建：**画布恒为深空**（见 §2），浅色只改面板与标签配色。
- resize 不重建：`resize()` 只重设画布尺寸与 `fit`，位图原样复用。

**重建调度**：首次在 `requestIdleCallback` 里生成，期间先画背景色 + 核球辉光的临时占位，生成完替换；DPR 变化（拖到不同缩放的显示器）时同样走这条路，旧图保留到新图就绪，不白屏。

**为什么不做「按视口重建」**：拖面板时每帧重建 = 每帧 400ms，必然卡死。位图内容与视口无关是这张图能每帧只花一次 `drawImage` 的前提。

现在每节点每帧 2 次 `createRadialGradient`（`client.js:1049`、`1061`）是最大浪费，改 sprite 后应显著下降。

## 6. 验证方式

仓库**零自动化测试**，`package.json` 无 scripts。诚实说明验证手段就是这三条：

1. `node --check client.js`（语法）。
2. GUI 手测：插件是软链到工作区，改完刷新 http://127.0.0.1:5903 即生效；用 demo 数据集（`lib/host/demo.js`）看默认态。
3. 截图比对：用 ego-browser 取 1440×900 深色/浅色各一张，人工确认「像星系」而非「像线条」。

**判定标准**：截图在缩略图尺寸下能一眼认出是螺旋星系，这是本次唯一的验收条件。

### 6.1 写文档时已跑过的数值验证

这些不是计划，是**已经跑过的实测**（临时脚本，未入库），用来确认公式本身没写错：

| 检查 | 结果 |
|---|---|
| 正交投影矩阵 vs 逐点公式，5 组 yaw × 5 组 pitch × 2 组 scale × 5 个点（含 DPR 基准修正） | 最大偏差 `2.3e-13` — 等价 |
| `drawImage` 四角在 s=432, yaw=0.62, pitch=−0.58, c=(720,450) 的落点 | (820.6,780.2) / (1322.6,394.9) / (619.4,119.8) / (117.4,505.1) — 平行四边形，`2s(|cosY|+|sinY|)=1205.2 × 2s|sinP|(|cosY|+|sinY|)=660.4`，单位圆映射为半轴 `s=432` / `s|sinP|=236.7` 的椭圆（倾角 56.8° @ pitch=−0.58）—— 投影正确 |
| `Math.min(4, fit)` 的危害 | 1440×900 → `fit=360`；800×600 → `fit=240`；800×800 → `fit=320`。**都被夹到 4** → 盘面半径 `4×1.2×1.15 ≈ 5.5px` —— 确认必须去掉上限 |
| `fit` 与 `min(w,h)` 的比例 | `0.46·min/1.15 = 0.40·min`（R=1.15 时）；若 R=1.0 则是 `0.46·min`。文档中的「约 0.4·min」只对 R=1.15 成立 |
| 指数盘反演 `-h·ln(u1·u2)`，n=400k，h=0.28 | 均值 `0.5608`，理论 `2h=0.5600` —— 反演正确 |
| 节点半径 `r = 0.10 + (1-score/100)^1.35 · 0.92` | score 100→`0.100`，70→`0.281`，40→`0.562`，0→`1.020` —— 单调、落在盘内 |
| 弧宽恒定 `σθ = clamp(0.11/r, .06, .55)` | r=0.30/0.60/1.00/1.15 时弧宽恒为 `0.110`；r=0.12 处 `0.11/0.12≈0.917` 被**上限**截为 `0.55` —— 符合设计意图（内圈臂被压糊） |
| 盘缘裁切概率 | `P(r>1.15)=12.8%`；若位图跨度只做 `[-1,1]²`，`P(落方框外)=9.5%` → 圆周被裁成直边。故跨度取 `R=1.25` |
| `FOV` 出现位置 | 仅 `client.js:424`（定义）/`529`（computeFit）/`833`（project）三处，删干净无遗漏 |
| `p.scale` 的消费者 | 仅 `client.js:991` / `1043` / `1163` 三处（`ops_grep` 全仓确认） |
| 深度 `z2` 作为排序键 | 未加 `+1000` 偏移，符合正交设计；但加性混合下排序无视觉作用，层次必须由 §4.1 的深度调制提供 |

一个**已知副作用**（不是缺陷，但要知道）：`i=13°` 时对数螺旋从 r=0.2 到 r=1.0 转约 400°，即**臂要绕一圈多**。真实星系（如 M51）也是这个量级，视觉上会得到「卷得比较紧」的盘。若实施后觉得太卷，把 `i` 调到 18°–20°（`tan` 变大 → 同样半径转的角度变少 → 臂更舒展）即可，这是单参数调整。

## 8. 风险

| 风险 | 应对 |
|---|---|
| 浅色主题下星系不像星系 | **已裁决**：画布恒为深空（像一张天文照片嵌在浅色面板里），浅色只改面板/标签/边框。不要求画布反极性 |
| 盘面位图与节点错位 | 已用同一仿射矩阵消除（§4.1）；**三个坑**：DPR 基准必须用 `setTransform(dpr…)` + `transform(…)`、`cx/cy` 必须用 `this.w/2 / this.h/2` 而非 `draw()` 作用域里的 `h*0.48`、跨度必须 `R=1.25`。实施时**先只画盘面 + 十字准星验证对齐**，再上节点 |
| 2 万星点生成慢 | 生成放 `requestIdleCallback`，首帧先显示背景 + 核球辉光占位，旧图保留到新图就绪。位图与视口解耦，**resize/缩放/主题切换都不重建** |
| 边全隐藏后「关系」信息丢失 | 三件一起做：① hover 也驱动 `highlight`；② `pick()` 无精确命中时退化到 28px 内最近节点；③ top-12 边极淡常显（alpha 0.10） |
| 弱节点在内臂挤成实心带、糊掉旋臂 | 按 `score` 第 60 分位分流：前 40% 严格贴臂（结构骨架），其余按 `hash` 铺进弥散盘（见 §4.3） |
| 改 `lib/host/settings.js` 需重启 dsh web | 该项放最后单独一步；不想重启就留 TODO 到下次发布——该配置无害 |
